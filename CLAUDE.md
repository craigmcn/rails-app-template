# rails-app-template

A reusable Rails application template (`rails new -m template.rb`) plus a CLI wrapper (`bin/new-rails-app`) for scaffolding new Rails apps with Pundit + roles-based authorization and a choice of Clearance/Devise auth baked in. See README.md for usage.

Dated write-ups of past work live in [docs/HISTORY.md](docs/HISTORY.md), which isn't auto-loaded. A `/checkpoint` adds its narrative there; this file keeps current state only.

## Non-obvious constraints

- **Pins:** `gem "json", "< 3"` (json 3.x breaks ActiveSupport 8.1's encrypted-cookie decoding, so every request after the first 500s), and Pagy `~> 9.0` (v43 dropped the Backend/Frontend/extras API `pagy.rb` uses; 9.x has no `tailwind` extra). Revisit the json pin once Rails supports json 3.x.
- **Generated Selenium setups patch Capybara 3.40's `ChromeDriver#reset!`** for Chrome 158, which rejects its `Storage.clearDataForOrigin` `"*"` origin ([capybara#2865](https://github.com/teamcapybara/capybara/issues/2865)). On that error the patch clears all cookies, then the storage of the origin the page was on before reset. It's gated on `Capybara::VERSION <= 3.40.0`; drop it from `system_test_driver.rb` once a fixed Capybara ships. Cuprite gets `process_timeout: 30`, since Ferrum's 10s default flaked on CI runners.
- **Development Puma runs 1 thread** (`puma_dev_threads.rb`): multi-threaded dev Puma races Rails' lazy route drawing on the first concurrent requests after boot.
- **Rails 8.1 no longer generates `test/system/`**, so `system_test_driver.rb` writes the system-test harness itself for both frameworks. For RSpec, the driver is set with a `config.before(:each, type: :system) { driven_by ... }` hook, since `rspec-rails` overrides `Capybara.default_driver`.
- **`--action-text` implies Active Storage**, enforced in `template.rb` (`ACTIVE_STORAGE || ACTION_TEXT`), not only in the CLI.
- **MySQL credentials** are written into `config/database.yml` via `#to_json` so YAML-significant characters stay quoted, by `db_credentials.rb`, before `db_create.rb`.
- **Anything the developer should act on goes through `note_for_end`** (`support.rb`), not `say`: setup notes, then warnings, then the next command, so nothing scrolls off mid-run. They print from `at_exit`, because a failed generator aborts the process and that's when a queued warning matters most. `generate_deferring_readme` moves Clearance's and Devise's install readmes there, reopening the real `STDOUT` fd since the generator is a subprocess. Output from Rails' own `--css`/`--javascript` installers, which run before the template's callbacks, isn't captured.
- **CI must pass `--no-interactive`**: without a TTY, `TTY::Prompt` blocks forever.
- **No repo Gemfile:** `bin/new-rails-app` loads `tty-prompt` via `bundler/inline`, only on the interactive path.
- **Easy-to-get-wrong names:** the annotate gem is `annotaterb` (not `annotate_rb`), and `active_storage:install` is a rake task (`rails_command`), not a generator like `action_text:install`.
- **Rack::Attack registers its own middleware** from inside its initializer, since Rails builds the stack from `config.middleware` after initializers run.
- **Role names aren't configurable** on purpose: they're baked into generated method names (`User#admin?`, `#assign_default_role`) in `roles.rb`. Rename by hand after scaffolding.

## Key decisions

- **Rails' own generator flags, not a bespoke option system** — `--css`/`--javascript`/`--database` are passed through unfiltered to `rails new` rather than curated, so the tool stays current as Rails adds/changes bundler or DB options automatically. Only `--auth` and `--test` are invented flags, since Rails has no native equivalent.
- **Baseline mirrors production apps, not designed from scratch** — the default stack (Postgres, Clearance, Pundit, esbuild+Sass+Bootstrap, Minitest+Capybara, roles table) was extracted from `~/Web/community_bookshelf`, `bookshelf-islands`, and `bookshelf-api`, which had already hand-built this exact pattern independently three times.
- **Trust Rails 8 defaults, don't reimplement them** — dropped a planned `procfile.rb` module (Rails' `--css`/`--javascript` generators already wire up `Procfile.dev`/`bin/dev` correctly) and a planned `ci.rb` CI-workflow generator (Rails 8 already generates `.github/workflows/ci.yml` with Brakeman/rubocop/tests, and already adds brakeman/bundler-audit/rubocop-rails-omakase/capybara/selenium-webdriver to the Gemfile). `ci.rb` now only adds `dotenv-rails`/`letter_opener`, which aren't Rails defaults.
- **`.yarnrc.yml` with `nodeLinker: node-modules` written synchronously, not in `after_bundle`** — Yarn 4's default PnP linker broke Bootstrap's Sass `@import` resolution; the file must exist on disk *before* Rails' own `--css`/`--javascript` setup runs any `yarn` command, so it's a plain top-level `create_file` in `template.rb`, not deferred.
- **`--skip-admin` only skips the `/admin` namespace UI**, not the underlying roles data model — roles stay useful for Pundit policies even without an admin UI.
- **Devise views get hand-styled per CSS framework** (bootstrap/tailwind), matching Clearance's treatment; other `--css` values (bulma/postcss/sass/none) fall back to plain unstyled-but-functional markup rather than guessing at framework-specific classes.
- **`db:create` runs as its own first step (`db_create.rb`), separate from the final `db:prepare` (`db.rb`)** — Clearance's and Devise's install generators query the database directly while generating (e.g. Clearance's `users_table_exists?`), which crashes the whole `rails new` process with an uncaught exception if the database doesn't exist yet. `db:create` has to happen before those generators run, not just before the final migrate/seed step. Discovered because only SQLite combinations (where the DB file just gets created on first access) had been tested end-to-end — the default `postgresql` path hit this immediately.
- **Repo protection is enforced by the user's own local `pre-push` hook** (`~/.config/git/hooks/pre-push`, global `core.hooksPath`), not a GitHub ruleset — rulesets aren't even available on this private repo without GitHub Pro. Bootstrapping `main` on the brand-new (empty) GitHub repo therefore went through a PR rather than disabling anything: pushed the fix branch first, seeded `main` on GitHub via the API at the original commit, switched the default branch to `main`, then opened/merged a normal PR.
- **The driver check lives only in CI, not in the shipped system test** — a page that renders looks the same under either driver, so only asserting `Capybara.current_driver` catches a driver setup that is silently ignored (#44's RSpec bug). Shipping that assertion would break every app whose developer later switches drivers, so `test-template.yml` writes it as a throwaway file instead.
- **RSpec apps don't pass `--skip-test` to `rails new`** — so Rails still generates its `ci.yml` `test`/`system-test` jobs with per-database services/env. `ci_workflow.rb` only adapts them: Node/Corepack steps (plus `packageManager`) when there's a `package.json`, and RSpec run commands that run `bin/rails test:prepare` first, since `bundle exec rspec` alone never builds JS/CSS on a fresh checkout. `bin/ci` (`config/ci.rb`) gets the same rewrite, with its main step excluding `spec/system` to match Minitest's `bin/rails test`; Rails' optional commented system step runs them once uncommented. That rewrite runs even without a `ci.yml`, since `--skip-ci` still leaves `bin/ci`. Under Yarn 2+, `bin/ci`'s `yarn audit` step becomes `yarn npm audit --recursive` (plus `--no-deprecations` on Yarn 4, which fails on them by default). `test_rspec.rb` removes the unused `test/` dir. `rubocop.rb` runs `bin/rubocop -a` last (and warns about whatever it couldn't fix), since template and Clearance/Devise output otherwise fails the generated lint job; the template CI lints every leg.
- **New apps scaffold into the caller's current working directory**, not into this repo — `bin/new-rails-app` never `chdir`s. README now shows running it from the parent directory (`cd ..; rails-app-template/bin/new-rails-app my_app`) so the new app lands as a sibling, not nested inside this repo.
- **`bin/dev` needs patching, not just a `.env` file, to make `PORT` configurable** — Rails' `config/puma.rb` already reads `ENV.fetch("PORT", 3000)`, and dotenv-rails (added by `ci.rb`) loads `.env` early enough to reach it in the plain `bin/rails server` case. But when `--css`/`--javascript` bundling is in play, the generated `bin/dev` runs `foreman start --env /dev/null` specifically to stop foreman from double-loading `.env`, and then exports its own `PORT="${PORT:-3000}"` into the child process *before* Rails (and therefore dotenv) ever boots — so a developer's `.env` choice never reached Puma. `port.rb` detects that specific foreman variant (by its `# Default to port 3000 if not specified` comment) and prepends a `. ./.env` source line to bin/dev itself. Confirmed by actually generating apps across bootstrap+esbuild, tailwind+esbuild, and sass+importmap (which produces a different, older-style `bin/dev` that already loads `.env` itself and needs no patch — detected and skipped by the same marker check).

Issue #13 (closed) extended that matrix to cover MySQL/trilogy (with a non-default username/password, exercising `db_credentials.rb`), the sass CSS fallback (with `--no-pagy`), the webpack JS bundler, and a `non-default-options` leg that turns on every remaining option (`--css=bulma`, the only CSS value that loads its own pagy extra, plus `--action-text`, `--system-test-driver=cuprite`, `--no-rack-attack`/`--no-bullet`/`--no-annotate`, `--port`). That leg also checks the options took effect, not just that the app boots. The check uses an explicit `if grep ...; then exit 1` because `! grep` never fails a step under Actions' `bash -e`. The `rspec` leg uses cuprite so both drivers and both frameworks are covered. So every option is covered, but not the full cross-product. Left out on purpose because our template code treats them like a tested sibling: mariadb (same as mysql), bun/rollup (passed straight to `rails new`), postcss (same views as sass). Issue #48 (closed): every app ships a home-page system test (`test/system/home_test.rb` / `spec/system/home_spec.rb`), Minitest legs run `bin/rails test:all`, and a CI-only test asserts `Capybara.current_driver` matches each leg's `expected_driver`. Covered: Minitest + selenium, Minitest + cuprite, RSpec + cuprite; RSpec + selenium is the one pair not run.
- Issue #50: each app's generated `ci.yml` runs its tests and lints clean (see the `--skip-test` key decision). The template's CI checks it statically on every leg; it never runs it. A one-off private throwaway repo proved it green on GitHub for a Minitest and an RSpec app. Re-run that proof by hand after a Rails upgrade changes `ci.yml.tt`, and scaffold with a patched Ruby, since Brakeman flags a `.ruby-version` with a known CVE. Known gap ([#52](https://github.com/craigmcn/rails-app-template/issues/52)): MySQL/trilogy apps with a non-default `--db-username`/`--db-password` still fail their generated CI, because Rails' `mysql` service uses an empty root password.
