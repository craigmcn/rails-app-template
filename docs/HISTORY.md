Also documented (README Prerequisites/Troubleshooting) the remaining failure mode that can't be auto-fixed — the database server itself not running.

- `services.rb` + `lib/generators/service/*`: a flattened service-object convention (single layer, no separate actions layer, modeled loosely on a heavier two-layer Actions/Services framework seen in another codebase) — `app/services/application_service.rb` defines `ApplicationService` (`.call(args, deps)`, per-subclass `Error`, dependency-injection override of nested service calls via the `deps` hash for testing) plus `dry-schema`-based argument validation via a `SCHEMA` constant and `define_schema`. Authorization intentionally stays in the controller (Pundit), not in services. `rails generate service Context::Name` (installed via `Rails::Generators::NamedBase`) emits the service plus a matching Minitest or RSpec test, chosen at scaffold time from `--test`. Verified end-to-end for both `--test=minitest` and `--test=rspec` (generator output, `dry-schema` validation raising/passing, generated test running green). Copilot's PR review on #7 caught a real bug (fixed): `validate!` originally ran before checking for a `deps` override, so overriding a service for tests couldn't bypass its own schema validation — `self.call` now resolves `effective_instance` first and only validates when it's a real instance of the class being called (`instance.instance_of?(self)`), confirmed by re-scaffolding and exercising all three paths (real call validates, valid args succeed, override bypasses validation).

## Completed (2026-09-08)

- `bin/new-rails-app` is now interactive by default: any option not passed as a flag (including the app name) is prompted for via [tty-prompt](https://github.com/piotrmurach/tty-prompt) — select lists for closed choices (`--auth`, `--test`, `--database`, `--css`, `--javascript`), yes/no for `--skip-admin`/`--bullet`, free text for the app name/`--port`, and a summary + confirmation before `rails new` runs. A new `--no-interactive` flag restores the old fail-fast-on-missing-options behavior for CI/scripting; passing any flag on the command line still skips just that one prompt, so partial invocations work as before.
- Added two new toggleable options, both pure additive changes with no interaction with the existing auth/css/js/database matrix: `--bullet`/`--no-bullet` (Bullet N+1 query detector, default on, `lib/template/ci.rb`) and `--port` (dev server port baked into `.env`/`.env.sample`, default 3000, `lib/template/port.rb`). Both flow through as new `SCAFFOLD_BULLET`/`SCAFFOLD_PORT` env vars, same handoff mechanism as the existing `SCAFFOLD_*` vars. `lib/template/readme_claude_md.rb`'s generated README/CLAUDE.md now reflect the actual chosen port and whether Bullet is present, rather than hardcoding `3000`/always mentioning Bullet.
- Considered making role names (admin/moderator/member) configurable too; decided against it — they're baked into generated method names (`User#admin?`, `#assign_default_role`) in `lib/template/roles.rb`, not just data, so making them configurable would mean templating method-name generation rather than substituting a value. Trivial to rename by hand post-scaffold instead.
- `tty-prompt` is pulled in via `bundler/inline` inside `bin/new-rails-app` itself (only when the interactive path actually runs), not a repo-level `Gemfile` — this repo has no `Gemfile` of its own (it's a bare script + `rails new` template, not a bundled app), and `bundler/inline` auto-installs the gem on first use without adding persistent repo dependencies.
- Added six more toggleable options, each verified end-to-end (not just `ruby -c`) by actually scaffolding apps with them on: `--active-storage`/`--no-active-storage` (`lib/template/active_storage.rb`, runs `rails_command "active_storage:install"` — note this is a rake task, not a Thor generator, unlike Action Text), `--action-text`/`--no-action-text` (`lib/template/action_text.rb`, `generate "action_text:install"`; forces `--active-storage` on too, since Action Text's `rich_text_content` references `active_storage_blobs`), `--rack-attack`/`--no-rack-attack` (`lib/template/rack_attack.rb`, default on — baseline IP + login throttles, `Rails.application.config.middleware.use Rack::Attack` added from inside the initializer itself since Rails builds the middleware stack from `config.middleware` after all initializers run), `--system-test-driver=selenium|cuprite` (`lib/template/system_test_driver.rb`), `--pagy`/`--no-pagy` (`lib/template/pagy.rb`, default on), and `--annotate`/`--no-annotate` (`lib/template/ci.rb`, default on — gem is `annotaterb`, not `annotate_rb`, easy to get wrong since the CLI/repo brand themselves as "AnnotateRb").
- **Discovered while testing, unrelated to any one option**: Rails 8.1.3.1 no longer scaffolds `test/system/`/`application_system_test_case.rb` by default at all (confirmed against a plain `rails new` with no template) — a change from the CLAUDE.md's prior assumption ("Rails' own test scaffold... is generated by `rails new`"). `system_test_driver.rb` now always writes the system-test harness itself from scratch (both Minitest and RSpec) rather than patching Rails-generated content, which is more robust to this kind of drift anyway.
- **Discovered while testing**: Pagy is currently at v43, a ground-up rewrite (`Pagy::Method`, no more `Pagy::Backend`/`Pagy::Frontend`, no `pagy/extras/*` mechanism at all) — `pagy.rb` deliberately pins `~> 9.0`, the last line using the Backend/Frontend/extras API this file is written against. Also: Pagy 9.x never shipped a `tailwind` extra (only `bootstrap`/`bulma`) — an initial `pagy/extras/tailwind` require was a `LoadError` waiting to happen, caught by scaffolding a `--css=tailwind` app.
- Added `--db-username`/`--db-password` (MySQL/trilogy only, default `root`/blank) after a real `bin/new-rails-app` run against `--database=mysql` failed immediately with `Access denied for user 'root'@'localhost'` — Rails' own default `config/database.yml` for mysql2/trilogy hardcodes `username: root` with a blank password and no local-OS-user fallback the way Postgres's trust-auth default has, so any MySQL server whose root user needs a real password (the common case) fails `db:create` with no working default to fall back on. `lib/template/db_credentials.rb` patches those two lines in `config/database.yml` synchronously (like `.yarnrc.yml`), applied first, before `db_create.rb`, since `db:create` and the auth generators right after it both need working credentials already in place. No-ops entirely for non-mysql-family databases. Verified the file patching end-to-end (correct username/password land in `config/database.yml`); couldn't verify a fully successful `db:create` against a real MySQL server in this environment (local mysql2 gem has an unrelated native-library mismatch against the installed MySQL 8.4 — a pre-existing environment issue, not caused by this change).

## Completed (2026-09-14)

- Fixed an intermittent 500 on the very first page load of a freshly-scaffolded app under `bin/dev` (`ArgumentError`/`RoutingError`, varying between runs — a genuine race, not a deterministic bug). Root cause, confirmed by firing three concurrent `curl` requests at a fresh boot (reproduced the failure) vs. one at a time (never failed): Rails' own generated `config/puma.rb` defaults to 3 threads in every environment, and Puma's multi-threaded dev server races against Rails' lazy route-drawing/autoloading on the first request(s) after boot — a browser's simultaneous initial requests (the page + `favicon.ico` + Chrome's `.well-known/appspecific/com.chrome.devtools.json` probe) can land on different threads while routes/constants are still being initialized for the first time. `lib/template/puma_dev_threads.rb` pins development to 1 thread (`RAILS_ENV`/`RACK_ENV`-gated, so other environments keep Rails' own `RAILS_MAX_THREADS`-driven default of 3) — confirmed the same concurrent-request burst no longer errors once threads are pinned to 1, both by hand-patching a running app and by re-scaffolding fresh through the template and repeating the test.
- Fixed a second, unrelated 500: after the puma-threads fix, any *navigation* past the first page load (clicking a link, submitting a form) still 500'd, deterministically, with the same misleading unstyled/traceless error page as the intermittent bug above (even with `config.consider_all_requests_local = true`) — because the exact same underlying failure also breaks rendering Rails' own debug-exceptions page. Root cause, found by driving the app in-process with `Rack::Test` and `config.action_dispatch.show_exceptions = :none` so the real exception (not a rescued/reformatted one) could be caught directly: `json` gem 3.x changed `JSON.parse`'s call signature in a way Rails 8.1.3.1's `ActiveSupport` isn't compatible with, and *every* encrypted cookie (session, CSRF) is JSON-decoded via `ActiveSupport::Messages::Metadata#deserialize_from_json` on every request past the first cookie-less one — an unconstrained Gemfile resolves `json` to 3.x, so any request carrying a cookie raises `ArgumentError: wrong number of arguments (given 2, expected 1)` deep inside `JSON.parse`. `template.rb` now pins `gem "json", "< 3"` synchronously (alongside `.yarnrc.yml`, before any `apply`), forcing Bundler to resolve `json (2.21.2)` instead — confirmed fixed by re-running the same `Rack::Test` repro (multi-request navigation with persisted cookies) against a freshly re-scaffolded app. Revisit the pin once Rails/ActiveSupport officially supports json 3.x.

## Completed (2026-10-12)

- Fixed the scaffolding-complete message telling the developer to run `bin/dev` without first `cd`-ing into the new app — `rails new` runs in the directory `bin/new-rails-app` was invoked from and creates the app as a subdirectory there; the generator process itself ends up with the new app dir as its cwd, but that's irrelevant to the *caller's* shell, which never left the parent directory. `readme_claude_md.rb`'s final "ready"/"was scaffolded" messages now prepend `cd #{app_dir}` before `bin/dev`.
- Fixed Devise's own `devise:install` generator readme ("...manual setup may be required...") printing immediately, then scrolling off screen under every subsequent generator's output (admin, rack_attack, pagy, tests, seeds, db:prepare, README/CLAUDE.md generation) — by the time scaffolding finishes, a developer never sees it. `generate "devise:install"` shells out to a real `rails generate` subprocess (`Rails::Generators::Actions#generate` → `rails_command` → `Thor::Actions#run` → `Kernel#system`), so Ruby-level `$stdout` reassignment doesn't capture it — only reopening the real `STDOUT` file descriptor does, since `system()`'s child inherits the OS-level fd, not Ruby's `$stdout` global. `auth_devise.rb` now reopens `STDOUT` to a tempfile around that one `generate` call, splits the captured text on the two `===...=` separator lines Devise's readme is boxed in (keeping the surrounding "create ..." log lines printing immediately as before), and stashes the boxed readme text in `@devise_install_readme` for `readme_claude_md.rb` to print as the literal last thing in scaffolding output. Caught a real `String#split` footgun while verifying: `split` drops a *trailing* empty string by default, and the text after the second separator is empty (end of capture) — `parts.length` silently came back `2` instead of `3` until passing a `-1` limit to `split` to keep it. Verified end-to-end (not just `ruby -c`) by re-scaffolding a fresh Devise app repeatedly and grepping the full console output for the readme marker text, confirming exactly one occurrence, at the very end.

## Completed (2026-11-08)

- Fixed CI's scaffold-matrix workflow (`test-template.yml`) hanging indefinitely instead of just running slowly — reported as "the CI scaffold matrix tests take waaay too long." Root cause: the Sept 8 interactive-CLI rewrite (`bin/new-rails-app`) made missing options prompt via `TTY::Prompt` by default, but the workflow's "Scaffold app" step never passed `--no-interactive`; in the Actions runner (no TTY on stdin), `TTY::Prompt` blocks forever waiting for input that never arrives. Every matrix leg has been stuck this way since that commit — one run sat `in_progress` for almost a month before being noticed. Fixed by adding `--no-interactive` to the scaffold command in `test-template.yml`.
- A background code review caught, and this fixed, two real bugs introduced earlier in this branch: (1) `--system-test-driver` had no effect for `--test=rspec` — `spec/support/system_tests.rb` was written but never required by `rails_helper.rb` (rspec-rails comments out its `spec/support/**/*.rb` glob require by default), *and* even once required, setting `Capybara.default_driver` alone doesn't work against `rspec-rails`'s `SystemExampleGroup`, which always calls `driven_by(DEFAULT_DRIVER) unless @driver` in its own `before` hook — the fix is a `config.before(:each, type: :system) { driven_by :name }` hook instead, which this branch's own earlier "verified end-to-end" claim had missed because that verification never actually ran an RSpec system spec. Caught only by writing and running a real system spec against a freshly scaffolded app (`expect(Capybara.current_driver).to eq(...)`), not by static reading — the first failure mode (never required) and the second (overridden anyway) look identical from the outside until you actually execute a test. (2) `auth_devise.rb`'s STDOUT-reopen capture around `generate "devise:install"` silently swallowed all of that generator's output if it raised — fixed by capturing the exception, printing whatever was captured, then re-raising, so a failure still shows the same "create ..." context it did before the capture was added.

- GitHub Copilot's automated PR review on #44 caught two more real bugs (triaged against our own independent review, which also caught the system-test-driver issue above independently): (1) `db_credentials.rb` interpolated the MySQL username/password into `config/database.yml` unquoted — a value containing YAML-significant characters (`:`, `#`, quotes, backslash) could produce invalid YAML or silently parse to the wrong value. Fixed by passing both through `#to_json`, which emits a double-quoted, escaped scalar that's valid YAML as well as JSON — verified by scaffolding with a username/password containing `:`, `#`, quotes, and a backslash, then round-tripping the generated file through `YAML.unsafe_load_file` and confirming the parsed value matches exactly. (2) `template.rb` applied `active_storage.rb`/`action_text.rb` as fully independent flags; `bin/new-rails-app` forces `--active-storage` on whenever `--action-text` is set, but that guard only lives in the CLI, not in `template.rb` itself — invoking the template directly (or hand-setting `SCAFFOLD_*` env vars) with only `SCAFFOLD_ACTION_TEXT=true` would apply Action Text without the Active Storage tables it needs. Fixed by changing `template.rb`'s `active_storage.rb` apply condition to `ACTIVE_STORAGE || ACTION_TEXT` — verified by scaffolding directly via `rails new -m template.rb` with only `SCAFFOLD_ACTION_TEXT=true` set and confirming `active_storage:install` now runs before `action_text:install`.
