## Completed (2026-09-14)

- Fixed an intermittent 500 on the very first page load of a freshly-scaffolded app under `bin/dev` (`ArgumentError`/`RoutingError`, varying between runs — a genuine race, not a deterministic bug). Root cause, confirmed by firing three concurrent `curl` requests at a fresh boot (reproduced the failure) vs. one at a time (never failed): Rails' own generated `config/puma.rb` defaults to 3 threads in every environment, and Puma's multi-threaded dev server races against Rails' lazy route-drawing/autoloading on the first request(s) after boot — a browser's simultaneous initial requests (the page + `favicon.ico` + Chrome's `.well-known/appspecific/com.chrome.devtools.json` probe) can land on different threads while routes/constants are still being initialized for the first time. `lib/template/puma_dev_threads.rb` pins development to 1 thread (`RAILS_ENV`/`RACK_ENV`-gated, so other environments keep Rails' own `RAILS_MAX_THREADS`-driven default of 3) — confirmed the same concurrent-request burst no longer errors once threads are pinned to 1, both by hand-patching a running app and by re-scaffolding fresh through the template and repeating the test.
- Fixed a second, unrelated 500: after the puma-threads fix, any *navigation* past the first page load (clicking a link, submitting a form) still 500'd, deterministically, with the same misleading unstyled/traceless error page as the intermittent bug above (even with `config.consider_all_requests_local = true`) — because the exact same underlying failure also breaks rendering Rails' own debug-exceptions page. Root cause, found by driving the app in-process with `Rack::Test` and `config.action_dispatch.show_exceptions = :none` so the real exception (not a rescued/reformatted one) could be caught directly: `json` gem 3.x changed `JSON.parse`'s call signature in a way Rails 8.1.3.1's `ActiveSupport` isn't compatible with, and *every* encrypted cookie (session, CSRF) is JSON-decoded via `ActiveSupport::Messages::Metadata#deserialize_from_json` on every request past the first cookie-less one — an unconstrained Gemfile resolves `json` to 3.x, so any request carrying a cookie raises `ArgumentError: wrong number of arguments (given 2, expected 1)` deep inside `JSON.parse`. `template.rb` now pins `gem "json", "< 3"` synchronously (alongside `.yarnrc.yml`, before any `apply`), forcing Bundler to resolve `json (2.21.2)` instead — confirmed fixed by re-running the same `Rack::Test` repro (multi-request navigation with persisted cookies) against a freshly re-scaffolded app. Revisit the pin once Rails/ActiveSupport officially supports json 3.x.

(2) `template.rb` applied `active_storage.rb`/`action_text.rb` as fully independent flags; `bin/new-rails-app` forces `--active-storage` on whenever `--action-text` is set, but that guard only lives in the CLI, not in `template.rb` itself — invoking the template directly (or hand-setting `SCAFFOLD_*` env vars) with only `SCAFFOLD_ACTION_TEXT=true` would apply Action Text without the Active Storage tables it needs. Fixed by changing `template.rb`'s `active_storage.rb` apply condition to `ACTIVE_STORAGE || ACTION_TEXT` — verified by scaffolding directly via `rails new -m template.rb` with only `SCAFFOLD_ACTION_TEXT=true` set and confirming `active_storage:install` now runs before `action_text:install`.

## Chrome 158 system-test fixes (2026-11-25)

- GitHub's runner image with Chrome 158 failed every Selenium system test in teardown: Capybara 3.40's `ChromeDriver#reset!` clears storage with origin `"*"`, which Chrome 158 rejects. Upstream has the issue (teamcapybara/capybara#2865) and an open PR (#2868), but no release. `system_test_driver.rb` now writes a version-gated patch into generated Selenium setups that follows #2868's approach. The first version cleared the storage of whatever page the browser was on at reset. Review found localStorage still leaked when a test ended with an alert open, on a second window, or on a `data:` page (reading the page also dismissed the alert before Capybara could accept it). The patch now clears the app's own origins instead: Capybara's server and `app_host`. Verified on local Chrome 158 with throwaway leak tests for all four cases (plain, alert, second window, `data:`) in Minitest and RSpec apps. The three new cases failed on the first version.
- The RSpec + Cuprite leg flaked with `Ferrum::ProcessTimeoutError` (no websocket URL within 10s), on PR runs and on `main`. Generated Cuprite drivers now pass `process_timeout: 30`. A first attempt set it in our own `Capybara.register_driver(:cuprite)` block and CI still timed out at 10s: Rails' `driven_by :cuprite` registers its own driver under that name, so that block (window size included) had never applied. The option now goes through `driven_by :cuprite, options: { process_timeout: 30 }`, and the CI driver check asserts Ferrum receives 30 (fails on the old setup, which reported 10).

## No hardcoded MySQL socket (2026-11-27)

- Issue #71: `rails new` hardcodes the first MySQL socket path that exists on the scaffolding machine (`/tmp/mysql.sock` first). For trilogy it goes in development/test, and Rails' Trilogy adapter drops `host` whenever a socket is set, so the generated CI's `DATABASE_URL` host was ignored and every test job failed with `ENOENT ... /tmp/mysql.sock`. For mysql2 it replaces `default:`'s `host:` line, so production lost `DB_HOST` too. `db_credentials.rb` now deletes any `socket: /...` line and writes `host:` plus an opt-in `socket: <%= ENV["DB_SOCKET"]&.to_json %>` into `default:`, the shape a socket-less (Linux) scaffold already had. TCP was chosen over moving the detected path into `.env`: local installs (Homebrew included) listen on `127.0.0.1:3306`, and a `.env` socket would also have broken the template CI's own `db:create` against a dummy socket.
- Verified on this Mac (real `/tmp/mysql.sock` present) with trilogy and mysql2 apps against a throwaway server: both scaffolds had the socket path before the fix and none after, connected over TCP via `DATABASE_URL`, passed their tests, and connected through the socket with `DB_SOCKET` set (plus `DB_HOST=localhost` for mysql2). The mysql-devise leg plants an empty `/tmp/mysql.sock` before scaffolding so Rails' detection fires on CI too.
- Review follow-ups: the socket/host rewrite only runs when the rewritten `password:` line is there to anchor it (otherwise Rails' lines stay and the warnings fire, instead of leaving no host at all); a duplicate `host:` line now warns; `DB_SOCKET` is `.to_json`-quoted like the credentials; CI checks the mysql2 shape too (a `rails new --minimal --skip-bundle -m` that applies only `support.rb` + `db_credentials.rb`, which fails on main) and asserts the test env resolves to host `127.0.0.1` with no socket.

## Scaffolding without a UTF-8 locale (2026-11-28)

- Issue #68: with `LANG`/`LC_ALL` unset or `C`, Ruby's `Encoding.default_external` is US-ASCII, and Thor's `apply` reads each template module with it, so the first module with an em dash in a heredoc (`port.rb`, by then) failed with "invalid multibyte character" and left a half-generated app behind. `template.rb` now sets `Encoding.default_external = Encoding::UTF_8` before its first `apply`, which covers direct `rails new -m template.rb` use as well as the CLI.
- The issue also suggested having `bin/new-rails-app` force a UTF-8 locale for `rails new`. Not needed: under the C locale, a sass+importmap Minitest app and a devise+tailwind RSpec app both scaffolded, wrote valid UTF-8 files, linted clean, booted in development and production, and passed their tests (subprocesses included). Forcing a locale would also depend on which locale names the machine has installed.
- The `css-sass-fallback` leg (the issue's repro flags) now scaffolds with `LC_ALL=C`, after a step proves that leaves Ruby on US-ASCII.
